# Backend: краткое задание для субагента

## Цель и состояние

Небольшой backend: **FastAPI → RabbitMQ → Celery worker → PostgreSQL**.
На 11.10.2026 реализованы загрузка/нормализация, три таблицы Alembic, чтение/health,
publisher и `process_image`. По запросу пользователя добавлены слои API/service/repository,
ORM вынесен в `tables.py`, сессия БД внедряется через FastAPI Depends из `db.py`.
Утверждены RF-DETR Small → ViT-B/16 → Florence-2 base-ft. Worker в профиле
`processing` запускается явно; реальный GPU-smoke пока не выполнен.
Проверки настоящих PostgreSQL/RabbitMQ/Celery используют синтетические модели.

Сначала прочитать [AGENTS.md](AGENTS.md), затем нужные разделы
[PROJECT_PLAN.md](PROJECT_PLAN.md) и [infrastructure.md](infrastructure.md).
Проверить Git status, существующие код/конфиги и [README.md](README.md).
Этот файл задаёт рамки делегирования, но сам по себе не поручает запускать модели.

## Что сделать

1. Четыре сервиса в `compose.app.yaml`: `backend`, `db`, `rabbitmq`, `worker`.
   PostgreSQL/RabbitMQ и файлы изображений — в постоянных volumes.
2. SQLAlchemy/Alembic: `images`, `jobs`, `model_results`. Точные поля и форматы —
   разделы 4–5 плана. Уникальность `(job_id, stage)` и явные статусы обязательны.
3. API: `POST /images` (multipart, `202`), `GET /jobs/{job_id}`, `GET /health`.
   Проверять фактический формат, лимиты, EXIF; сохранять оригинал и RGB PNG-копию.
4. При загрузке одной транзакцией сохранить image/job/три pending-этапа.
   В `jobs` — поля публикации; один лёгкий publisher в lifespan API повторяет
   отправку pending-заданий с backoff и publisher confirms. API не выполняет инференс.
5. Celery: одна `process_image(job_id)`, очередь `inference`, concurrency 1,
   prefetch 1, late ACK, reject-on-worker-lost, JSON. Отдельный result backend
   не нужен: предметные результаты и статусы находятся в PostgreSQL.
6. В задаче последовательно запускать детектор → классификатор всех crops →
   аннотатор. Каждый этап — свежий subprocess с завершением до следующего.
   CUDA не инициализируется в родителе/prefork-пуле Celery.
7. Записывать результаты каждого этапа сразу; не терять их при последующей ошибке.
   Повторно доставленный конечный job пропускать; незавершённый восстанавливать
   только после получения общего inference-lock и повторного чтения БД.
   Готовые этапы неизменяемы; максимум две попытки обработки задания.
8. Завершение, timeout, сбой БД и requeue реализовать по разделу 6 плана.
   Сообщение не подтверждать до commit результата; простой общий `except` не
   гарантирует повторную доставку. Проверить этот сценарий через реальный брокер.

## Минимальные файлы и ограничения

`main.py` собирает приложение; `api.py` содержит HTTP/DI; `service.py` — бизнес-логику,
`repository.py` — запросы, `db.py` — подключения/сессию, `tables.py` — ORM.
Также `schemas.py`, `storage.py`, `tasks.py`, `processing.py`, `models.py`,
`settings.py`, миграции и тесты. Лишние обёртки и универсальные реестры не нужны.
Checkpoint и хеши зафиксированы в `checkpoints.json`, ImageNet-словарь — в
`imagenet_labels.json`. Worker использует два окружения с отдельными Transformers.
Старые nullable checkpoint завершаются `model_not_configured`; новые фиксируются до publish.

Общий со сравнениями `storage/locks/inference.lock` защищает модельных потомков
до их полного завершения. Одна модель в RAM/GPU, batch 1. Рамки относятся к
сохранённой нормализованной копии; классификация связана через `object_id`.
Исходные detector labels и `raw_caption` не заменять производными значениями.

Сейчас не делать UI, overlay/выдачу изображения, поиск, согласование, обучение,
Redis, Beat, Flower и универсальные реестры/плагины. Не менять исторические
результаты сравнений. Не обещать exactly-once: повтор незаписанного этапа допустим.

## Приёмка и отчёт субагента

Проверки первого этапа (11.10.2026): 11 CPU-тестов; с настоящими PostgreSQL и
RabbitMQ — 25 тестов всего (14 интеграционных), все прошли. Ruff check и format
по репозиторию, Compose config обоих стеков и Alembic check прошли. Отдельно
проверены реальные остановки БД/брокера, повторное подключение и down/up с
сохранением файлов, записей и очереди. Тестовая зависимость Starlette выдаёт
одно предупреждение об устаревании HTTPX TestClient. Модельных запусков не было;
проверка отказа незарегистрированного worker сохраняется как защита конфигурации.
Последующая интеграция с отдельным prefork worker и mock subprocess описана в README;
она не заменяет реальный smoke тройки.

Сначала CPU/mock, затем настоящие PostgreSQL + RabbitMQ + отдельный Celery worker:
загрузка/чтение, дубли, потеря publish/ACK, сбои БД/брокера/worker и перезапуск volumes.
Eager mode не заменяет интеграцию. Реальный smoke трёх моделей — только по явно
поставленной задаче; не запускать 12 моделей или пересчёт сравнений автоматически.

или планируемый сервис за работающую реализацию.
