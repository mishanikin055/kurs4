# Backend: текущая простая версия

Уточнение от 19.10.2026: FastAPI → RabbitMQ → Celery → файлы в volume → PostgreSQL.
Без создания заданий, статусов и ошибок инференса в БД; без callback.
По уточнению 20.10.2026 frontend автоматически ожидает готовый комплект через GET.
Перед изменениями читать AGENTS.md, текущий код, PROJECT_PLAN.md и README.md.
Этот файл сам по себе не поручает делегирование или запуск моделей.

## Ответственность

- `api.py`: загрузка, health брокера, GET результата с уточнениями, скачивание файлов/ZIP.
- `service.py`: валидация/сохранение входов, непосредственная публикация с confirms,
  проверка безопасного пути для скачивания. Нет сессии БД в HTTP-потоке.
- `repository.py`: `ImageRepository`, чтение/вставка только `processed_images`.
- `processing.py`: параллельный аннотатор и ветка детектор → классификатор, lock,
  ожидание обеих веток, готовый комплект, затем commit.
- `storage.py`: оригинал/RGB PNG, COCO-рамки и атомарная публикация комплекта.
- `tasks.py`: очередь, одна задача `process_image(image_id)`, startup/readiness/requeue.
- `runtime.py`/`models.py`: существующие постоянные процессы выбранных трёх моделей.
- `tables.py`: только активный `ProcessedImage`; исторические схемы остаются в миграциях.

## Обязательные свойства

Входы сохраняются в `image_data/<image_id>/`; очередь содержит только `image_id`.
В БД на загрузке ничего не создаётся. `202` выдаётся после RabbitMQ confirms.
После трёх моделей основная копия **всегда** в `image_data/results/<image_id>/`:
`original`, `normalized.png`, `detection.png`, `results.json` и `crops/<object_id>.png`.
Список имён вырезок — поле `crops` в JSON; PNG соответствуют входу классификатора
с тем же отступом до преобразований ViT. Пустая детекция — пустая папка `crops`. Папка публикуется
атомарно, затем одной транзакцией добавляется строка `processed_images`.
В БД только пути/размеры и JSONB `models`, `detection`, `classification`, `annotation`.

Дубликат готового UUID не повторяет модели. После сбоя commit БД готовый комплект
используется повторно. До публикации комплекта все этапы могут повториться после
сбоя. Ошибка модели — только лог Celery и сохранённые входы, без фиктивного успеха.
Нет прежнего outbox, восстановления отдельных этапов и счётчиков попыток в БД.

RF-DETR Small → ViT-B/16 выполняются последовательно; Florence-2 base-ft
параллельно описывает всё нормализованное изображение. По уточнению 19.10.2026
это заменяет прежний запуск аннотатора после классификации. Два потока только
координируют IPC; три процесса моделей резидентны. Concurrency/prefetch/batch 1:
одно изображение одновременно. Файлы и запись БД появляются только после обеих
веток. Обычная ошибка ждёт завершения соседней ветки; прерывание/IPC/OOM отменяют
запросы и требуют рестарта worker. Общий lock занят от
загрузки моделей до их завершения. Checkpoint/хеши/параметры — checkpoints.json;
до их смены завершить очередь. COCO bbox/labels и raw_caption не менять.
Crop расширять на 10% с каждой стороны; top-1 связывать с object_id.
Нет объектов — пустая классификация, аннотатор выполняется.
Ускорение и память при одновременном инференсе требуют отдельного GPU smoke;
прежний smoke подтверждал только последовательные вычисления.

По уточнению 20.10.2026 frontend автоматически запрашивает `GET /images/{image_id}`:
`404` — повтор через 2 секунды, успех — PNG/описание/таблица и остановка опроса.
При ошибке/40 мин ожидания — кнопка повторного ожидания; запрос ограничен 15 секундами.
Новая загрузка отменяет старое ожидание. GET вычисляет `refinement` по сохранённому
словарю ImageNet→COCO, не меняя исходный `label`, файлы, БД и raw_caption.
Несовместимые/неизвестные метки и точный повтор COCO оставляют колонку уточнения пустой.
Словарь проверяет совместимость классов, не фактическую правильность подтипа по фото.
По следующему уточнению 20.10.2026 сохранены две колонки: загрузка и результаты
под ней слева, изображение справа. Файл и папка выбираются в одну строку. Компактные панели при ширине от 1000 px занимают высоту окна; длинная таблица
прокручивается внутри панели. «Отправить» вне панели загрузки; на мобильном — один столбец.
Путь в volume в UI не показывается; `/jobs/...` и endpoint статуса не нужны.
Пользователь необязательно выбирает папку на
**своём компьютере**: после получения результата браузер автоматически сохраняет
четыре основных файла и папку `crops` в подпапку UUID. Папка, выбранная после обработки, тоже сохраняется сразу.
Без выбора/поддержки API и при ошибке записи доступна кнопка «Скачать ZIP»; результат
при ошибке сохранения остаётся видимым. Кнопок сохранения копии/показа результата нет. Основная копия в volume остаётся всегда.

## Проверка

Сначала CPU/mock-тесты и Ruff; затем отдельные настоящие PostgreSQL, RabbitMQ и
Celery worker с синтетическими моделями. Не использовать рабочую очередь в тестах.
Проверить запись в БД только после файлов/трёх этапов, ошибки без записей,
дубликаты, redelivery после сбоя БД, ручные скачивания и сохранность volume.
Настоящие модельные прогоны/полные сравнения не запускать без отдельной задачи.
