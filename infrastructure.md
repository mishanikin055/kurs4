# Инфраструктура: Docker, RabbitMQ, Celery и ресурсы

Текущий поток от 19.10.2026: загрузка → очередь → три модели → файлы в volume → БД.
[Архитектура](PROJECT_PLAN.md), [backend](backend.md), [команды](README.md).

## Пять сервисов приложения

`compose.app.yaml`: frontend (nginx), backend (FastAPI), db (PostgreSQL),
rabbitmq, worker (Celery). Профиль `processing` включает worker явно;
`compose.app.gpu.yaml` даёт только ему доступ к GPU текущей WSL.

| Сервис | Ответственность |
|---|---|
| frontend | Статические HTML/CSS/JS, порт localhost:8080, `/api/` proxy. Без volume/секретов/БД/весов. |
| backend | Загрузка в image volume, синхронная публикация RabbitMQ с confirms, ручные скачивания. Порт localhost:8000; без GPU и обращения к БД. |
| db | `processed_images`: только готовые результаты. Постоянный volume pgdata. Старые таблицы сохраняются как история. |
| rabbitmq | Одна durable очередь/exchange inference, persistent JSON, постоянный rabbitmq_data, фиксированный hostname. |
| worker | Один prefork consumer, concurrency/prefetch 1; три постоянных модельных процесса, последовательные вычисления. |

Общий `image_data` подключён backend и worker по `/var/lib/kurs4/images` на запись.
Входы: `<image_id>/original`, `normalized.png`. Итоги **всегда**:
`results/<image_id>/original`, `normalized.png`, `detection.png`, `results.json`.
Файлы публикуются полным комплектом до commit БД. После commit входной каталог
удаляется; копия результатов в volume остаётся. Дополнительная копия на компьютере
пользователя записывается браузером по кнопке, через API; никакой mount компьютера
в worker и дополнительный серверный каталог не нужны.

У backend зависимость только от здорового RabbitMQ; при загрузке БД не нужна.
У worker зависимости от db/rabbitmq; дополнительно до моделей проверяется таблица
processed_images. Миграции выполняются отдельной командой, не startup API.
БД и очередь не публикуют порты на хост. `down -v` не использовать для перезапуска.

DB outbox/publisher в lifespan удалён. Очередь содержит только image_id; consumer
вызывает process_image(image_id). Late ACK — после файлов и commit БД. При потере
БД/резидентного процесса worker останавливается и сообщение возвращается в очередь;
после готовых файлов повторяется только запись БД. Ошибки моделей остаются в логах,
промежуточных записей/статусов/ошибок в БД больше нет. Celery result backend не нужен.
Перед обновлением завершить прежнюю очередь с job_id старым worker, сохранить backup,
обновить образы, применить новую миграцию c81f0e392ab4 и пересоздать сервисы.

`storage/locks` — общий bind mount приложения и benchmark. Lock удерживается от
загрузки до полной остановки моделей. Веса read-only, HF offline, датасеты приложению
не нужны. Два Python-окружения внутри worker сохраняются; CUDA не загружается
в Celery prefork. При старте проверяются хеши, выполняются загрузка и прогрев моделей.
Недостаток RAM/VRAM не допускает подключения consumer. Лимит worker 5 GiB;
db/rabbitmq/backend — по 512 MiB, frontend — 64 MiB. Readiness требует после прогрева
не менее 768 MiB доступной RAM хоста, 512 MiB до cgroup-лимита по anon+kernel и
1 GiB свободной VRAM. Это не гарантирует отсутствие OOM на всех изображениях.
Перед benchmark остановить worker; до смены параметров/весов завершить очередь.

Секреты — только .secrets/app.env и игнорируемые локальные файлы; не печатать их
в чат/логи. Новый GPU smoke этой переделкой не разрешён. Интеграционные тесты
используют отдельные PostgreSQL/RabbitMQ и отдельный worker с mock-процессами.
Проверку новых файлов/БД/очереди не считать настоящим инференсом выбранных моделей.
Исторический короткий GPU smoke выполнен 13.10.2026; отчёты сохраняются.

## Существующие окружения сравнений

Рабочая копия `/home/mikhail/kurs4`, WSL2 Ubuntu 26.04, Bash.
Один основной `compose.yaml` содержит три ML-сервиса: detection, classification,
annotation. Дополнение `compose.gpu.yaml` подключает GPU текущей WSL через
`/dev/dxg`, `/usr/lib/wsl/lib` и `/usr/lib/wsl/drivers` read-only, без Docker socket.
Основной файл также используется для CPU-метрик/тестов/report-only/подготовки.
Команды — [README](README.md). Прежние Compose/shell-обёртки удалены.

### ML-образы

Три `*/Dockerfile` сохраняют базовый digest PyTorch/CUDA и точные requirements;
образы `kurs4-detection:v1`, `kurs4-classification:v1`, `kurs4-annotation:v1`.
Transformers детекции и аннотирования имеют разные версии, объединять их нельзя
без отдельной проверки. Entry point — Python, запуск прямым путём скрипта.
`init: true` собирает потомков; лимиты RAM — 6 GiB детекция/классификация,
7 GiB аннотирование. Данные/веса read-only, результаты/locks — writable.

Runtime `network_mode: none`, HF offline, токен не монтируется.
Явная подготовка использует `COMPARISON_NETWORK=bridge PREPARE_ACCESS=rw`
и `scripts/prepare.py <направление> --download`. HF-токен для новой загрузки
ImageNet подключается отдельным read-only mount `.secrets/hf_token`.
Не выводить токены в чат/логи и не включать их в образ/Git.
Локальная подготовка без сети также поддерживается.

После сборки записать фактические ID образов переменными DETECTION_IMAGE_ID,
CLASSIFICATION_IMAGE_ID, ANNOTATION_IMAGE_ID из `docker image inspect`.
JSON запуска фиксирует image ID, версии, исходники и Git revision/dirty status.
Данные не встраиваются в Docker context; `.dockerignore` исключает datasets,
веса всех трёх направлений, secrets, reports и исходные материалы.

### Память и процессы

RTX 4050 Laptop, 6141 MiB VRAM; Intel Core i5-12450H; хост 16 GiB RAM,
WSL видит около 7.6 GiB. Перед GPU-проверками измерять реальные available RAM,
свободную VRAM, cgroup limit и отсутствие конкурирующего инференса.
PyTorch allocated/reserved не равны полной памяти GPU/Windows-драйвера.
Подключение `/dev/dxg` не предполагает NVIDIA Container Toolkit; это настройка
именно текущей WSL, для другого Linux требуется собственный проверенный профиль.

Для сравнений строго одна модель в RAM/GPU, batch 1. `storage/locks/inference.lock` удерживается
модельным дочерним процессом до выхода; следующая модель стартует после завершения.
Остановка родителя должна завершить process group, а SIGKILL родителя не должен
освободить lock живого потомка. `empty_cache()` это требование не заменяет.
Cgroup OOM-kill и CUDA OOM должны иметь явный статус, неполный набор не становится
полным результатом. После прерывания новое имя сравнения, без сложного resume.

В приложении с 13.10.2026 разрешены три постоянно загруженные модели. По запросу
19.10.2026 Florence-2 выполняет инференс параллельно с веткой RF-DETR → ViT;
одновременно обрабатывается одно изображение, batch/concurrency/prefetch 1.
Два потока координатора обслуживают отдельные IPC-каналы; CUDA остаётся в
модельных процессах. Потомки наследуют lock на весь срок работы.
После потери координатора, ошибки IPC, таймаута или CUDA OOM перезапускается весь
worker: активные запросы отменяются, незавершённое сообщение возвращается в очередь.
Сохраняется только полный комплект; до его публикации все модели могут выполниться
повторно. Обычная ошибка модели дожидается второй ветки без публикации результата.
Остановка Docker освобождает модели; restart заново проверяет веса и прогревает их.
Прежний GPU smoke был последовательным; параллельные пики памяти и ускорение
не проверены. Для научных сравнений сохраняется одна модель и прежний порядок.

### Проверки и границы задачи

Схема приложения сокращена 12.10.2026: миграция `b7d91f4e20ac` удаляет избыточные
метаданные и top-k, сохраняя рамки, классы и аннотации. Перед обновлением рабочей
БД остановить backend/worker, сохранить backup PostgreSQL и volume изображений;
после миграции запускать только пересобранные контейнеры. Downgrade удалённые данные
не восстанавливает. Порядок запуска и форматы — README и PROJECT_PLAN.md.

По последнему указанию пользователя новые модельные запуски, пересчёт
метрик из исторических предсказаний и пересборка таблиц в текущей переделке
прекращены. Дополнительная реальная проверка — только по новой задаче.

Для текущих правок кода — локальные CPU/mock pytest в трёх Docker-окружениях,
Ruff check/format и Compose config. Ранее выполненные проверки метрик и smoke
12 моделей остаются историческими результатами, не командой на новый запуск.
Полные сравнения ради переделки не повторяются.
Контроль сохранности — `docs/refactoring-baseline.json`; исторические отчёты,
DOCX и source snapshots не изменяются. Mock/CPU и GPU результаты указывать отдельно.
GitHub Actions удалены по указанию пользователя, проверки выполняются локально.
