# Инструкции по курсовому проекту

## О проекте

«Программное средство детекции и классификации объектов и аннотирования изображений с использованием искусственной нейронной сети».
Текущий этап приложения: загрузка изображения через FastAPI, один детектор, один классификатор вырезок и один отдельный аннотатор; результаты всех этапов сохраняются в PostgreSQL. Изображения хранятся в постоянном volume со ссылками и метаданными в БД. Выдача изображений, overlay, UI, поиск и согласование сейчас не реализуются. Поиск остаётся частью исходного задания, отложенной на следующий этап.
Научная часть — три сравнительных анализа по четыре готовые модели: детекция, классификация и аннотирование. Обучение, fine-tuning и LoRA не входят в проект.

## Масштаб архитектуры

Нужна инфраструктура небольшого стартапа: **FastAPI + PostgreSQL + RabbitMQ +
Celery worker**, четыре отдельных контейнера. Инференс выполняется только в
Celery-задаче `process_image(job_id)`: три этапа последовательно, worker concurrency 1.
RabbitMQ доставляет задания; PostgreSQL хранит их статусы и результаты всех моделей.
FastAPI принимает загрузки и публикует сохранённые задания, но не запускает модели.
Пользователь утвердил RF-DETR Small, ViT-B/16 и Florence-2 base-ft; 12 участников научных сравнений
не требуют включения в приложение.

Не строить архитектуру большой исследовательской платформы. Не создавать много
лишних модулей, обёрток, диспетчеров и абстракций. Слои API/service/repository
для backend разрешены явным запросом пользователя от 11.10.2026; дополнительные
use-case и подобные слои не нужны. Новый файл нужен только при конкретной
ответственности. Не добавлять Redis, Celery Beat, Flower, сервис на каждую модель,
реестры плагинов, Kubernetes, сложные CI/CD и обязательные процессы согласования
без отдельной задачи. Один broker и один worker достаточны для первого этапа.

## Общие правила

Это курсовой проект. Приоритет — понятный код и простые команды запуска.
Для каждого сравнения предусмотрены четыре скрипта моделей и один общий
модуль. Расширяй существующие файлы; не создавай дополнительные обёртки,
диспетчеры, реестры, плагины и универсальные экспериментальные платформы.
Новый служебный файл допустим только для конкретной необходимой функции,
которую нельзя разумно разместить в существующей структуре; назначение
поясняется в README. Тесты и необходимый сторонний код метрик сохраняются отдельно.

По заданию от 11.10.2026 новые сравнения запускаются напрямую из
`scripts/{detection,classification,annotation}/`: четыре содержательных
скрипта моделей и `common.py` в каждом направлении. Каждый запуск — **один
проход**; новые классификационные скрипты поддерживают **только ImageNet**.
Старые GT/detector-crops, интервалы, полные результаты, исходные конфиги и
source snapshots сохраняются. Новые результаты — только `reports/runs/`;
старый результат модели не перезаписывать и не возобновлять. Автоматические
полные перезапуски ради рефакторинга запрещены. Рефакторинг сравнений отделён
от приложения; новый план приложения зафиксирован в PROJECT_PLAN.md. По последнему указанию пользователя от 11.10.2026
Word-экспорт не реализовывать: достаточно таблицы в консоли и CSV/Markdown.
Прежние DOCX и manifests сохранять. По следующему уточнению от 11.10.2026
в ходе этой переделки больше не запускать модели и не пересобирать сравнительные
таблицы; работать с кодом и CPU/mock-тестами. Дополнительные прогоны требуют
новой явной задачи пользователя. Актуальные команды — в README и `compose.yaml`,
доступ GPU текущей WSL — `compose.gpu.yaml`.

- Общение и проектная документация — на русском; код, идентификаторы и имена файлов кода — на английском. Основной язык — Python.
- Основная рабочая копия — `/home/mikhail/kurs4`, WSL2 Ubuntu 26.04; команды — Linux/Bash. Единственный репозиторий — https://github.com/mishanikin055/kurs4.git, существующий `origin`. Ветки — `codex/<task>`; до изменений проверить Git status и не затирать чужую работу.
- Приложение и сравнения запускаются в Linux Docker Compose. Стек приложения: FastAPI, PostgreSQL JSONB, SQLAlchemy/Alembic, RabbitMQ и Celery. Четыре сервиса: backend, db, rabbitmq, worker. Streamlit сейчас не нужен.
- Порядок: **детектор → классификатор всех вырезанных объектов → отдельный аннотатор**. Batch size 1. Одновременно строго одна модель в RAM/GPU; модельный дочерний процесс должен завершиться до следующего. Приложение и benchmark используют общий `storage/locks/inference.lock`.

## Состояние и завершение работы

На 09.10.2026 сравнения детекторов и классификаторов завершены; полный ImageNet — два круга, crops — ранее завершённые три. Ограничения описаны в classification/README.md и сохранённых научных отчётах. Автоматическое сравнение аннотаторов завершено: четыре checkpoint × один проход × 500 COCO-изображений, без новых CI. Человеческая оценка исключена пользователем; внешний набор не использован и указан как ограничение. Все три сравнения завершены в актуальном объёме; детали в annotation/README.md и сохранённых отчётах. На 11.10.2026 начата реализация backend: API загрузки/чтения/health, PostgreSQL/Alembic, файловое хранение и publisher RabbitMQ. Реализованы слои API/service/repository, process_image, адаптеры выбранной тройки, subprocess/lock и восстановление. Worker включается явно профилем processing, реальный smoke ещё не выполнен. UI и поиск не реализованы. Команды и проверки — в README. Статус сравнений описан в README соответствующих каталогов и отчётах.

Сначала маленький работающий вертикальный сценарий, затем расширения. Не создавать заглушки с фиктивным успешным результатом. Использовать типизацию, небольшие адаптеры, явные исключения и конфиги.

До команд проверять существующие инструменты и тесты. При наличии соответствующей конфигурации выполнять релевантные `python -m pytest`, `python -m ruff check .`, `python -m ruff format --check .` в выбранном окружении; после правки Markdown полный GPU-benchmark не нужен. Реальные model smoke и быстрые mock-тесты отмечать отдельно. Перед приёмкой приложения нужны интеграция настоящих PostgreSQL, RabbitMQ и отдельного Celery worker, затем smoke трёх выбранных моделей. Это не разрешение запускать модели в задаче планирования; новые прогоны требуют явной задачи пользователя. Повтор всех 12 моделей ради backend не нужен.

Обновлять затронутые активные инструкции, README, конфиги и manifests; крупные отклонения фиксировать в `docs/decisions.md`. В конце указать изменения, проверки и оставшиеся ограничения. Не писать «всё работает» после одних статических проверок.
