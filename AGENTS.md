## О проекте

«Программное средство детекции и классификации объектов и аннотирования изображений с использованием искусственной нейронной сети».
Текущий этап приложения: загрузка изображения через FastAPI, один детектор, один классификатор вырезок и один отдельный аннотатор; результаты всех этапов сохраняются в PostgreSQL. Изображения хранятся в постоянном volume со ссылками и метаданными в БД. После детекции сохраняется PNG с COCO-рамками; классификатор получает crop с отступами, GET вычисляет семантику COCO/ImageNet. По следующему запросу 12.10.2026 добавлены простой frontend в отдельном nginx-контейнере, HTTP-выдача PNG и endpoint статуса. Поиск остаётся частью исходного задания, отложенной на следующий этап.
Научная часть — три сравнительных анализа по четыре готовые модели: детекция, классификация и аннотирование. Обучение, fine-tuning и LoRA не входят в проект.

## Масштаб архитектуры

Нужна инфраструктура небольшого стартапа: **FastAPI + PostgreSQL + RabbitMQ +
Celery worker** и статический **nginx frontend**, пять отдельных контейнеров. Инференс выполняется только в
Celery-задаче `process_image(image_id)`: детектор → классификатор и параллельный
аннотатор, worker concurrency 1. RabbitMQ доставляет image_id; PostgreSQL хранит
только готовые результаты после файлов. FastAPI сохраняет входы и публикует
image_id с confirms, но не запускает модели.
Пользователь утвердил RF-DETR Small, ViT-B/16 и Florence-2 base-ft; 12 участников научных сравнений
не требуют включения в приложение.

Не строить архитектуру большой исследовательской платформы. Не создавать много
лишних модулей, обёрток, диспетчеров и абстракций. Слои API/service/repository
для backend разрешены явным запросом пользователя от 11.10.2026; дополнительные
use-case и подобные слои не нужны. Новый файл нужен только при конкретной
ответственности. Не добавлять Redis, Celery Beat, Flower, сервис на каждую модель,
реестры плагинов, Kubernetes, сложные CI/CD и обязательные процессы согласования
без отдельной задачи. Один broker и один worker достаточны для первого этапа.

## Уточнение пользователя: компактная БД (12.10.2026)

Следующее уточнение 12.10.2026 расширяет объём: сохранять PNG с COCO-рамками
сразу после детекции в image volume, до следующих моделей; worker имеет доступ
на запись. Crop классификатора расширять на 10% ширины/высоты с каждой стороны
в пределах изображения, исходный bbox не менять. Использовать семантический
словарь ImageNet→COCO (копия исторического mapping в backend): same/refinement/
conflict/unmapped/unavailable. Сохранять исходные ответы отдельно; при конфликте
или отсутствии соответствия учитывать COCO. Производную семантику вычислять
в GET, не расширяя БД. По следующему запросу того же дня HTTP-выдача PNG и UI
включены в объём; подробности в последнем уточнении ниже.

Не хранить top-k классификатора, scores, SHA изображений/весов, повторные размеры,
рамки вырезок, замеры этапов и общие параметры в БД приложения. Детекция содержит
`object_id`, `label`, `bbox` (xyxy в пикселях нормализованного PNG); классификация —
тот же `object_id` и один `label` либо `error`; `raw_caption` сохраняется неизменным.
`images`: UUID, два пути и размеры. `model_results`: составной PK `(job_id, stage)`,
статус, имя/ревизия модели, payload, ошибка. Поля восстановления доставки в `jobs`
сохранены. Checkpoint-хеши и параметры остаются в `backend/checkpoints.json`;
перед сменой параметров завершить очередь. Старые миграции и научные данные не менять.
Новая миграция необратимо удаляет лишние метаданные и альтернативные предсказания;
перед применением к рабочей БД остановить API/worker и сохранить backup.

## Уточнение пользователя: постоянные модели worker (13.10.2026)

Пользователь запросил ускорение через загрузку всех трёх моделей при старте Docker
worker, при условии достаточной оперативной и видеопамяти. Это отменяет прежний
запрет одновременного хранения моделей в памяти для приложения. Вычисления остаются
последовательными, concurrency 1, batch 1. Научные сравнения не менять и не повторять.
`backend/runtime.py` управляет тремя постоянными subprocess и локальным IPC;
разные Python-окружения моделей сохранены. CUDA не загружается в Celery prefork.
Веса проверяются один раз, модели загружаются и прогреваются до подключения consumer.
Общий lock удерживается весь срок жизни моделей: перед сравнением остановить worker.
При недостатке памяти запуск не проходит readiness; таймаут/потеря модельного
процесса или координатора требуют перезапуска worker и повторной доставки задания.
Результаты уже завершённых этапов сохраняются. Смена весов/параметров требует
завершения очереди и пересоздания worker. Контрольный GPU smoke текущей тройки
входит в этот запрос оптимизации; полные сравнения не входят.


## Уточнение пользователя: простое сохранение (19.10.2026)

FastAPI сохраняет входы в volume и непосредственно публикует image_id в RabbitMQ
с confirms. Задания/статусы/ошибки/промежуточные этапы в БД не создаются; callback
и polling нет. Worker выполняет RF-DETR Small → ViT-B/16 на всех вырезках и
параллельно Florence-2 base-ft; после обеих веток **всегда** сохраняет основной комплект в
image_data/results/<image_id>/: original, normalized.png, detection.png, results.json.
Только после публикации полного комплекта — одна запись processed_images с путями,
размерами и JSONB ответами/названиями и ревизиями моделей. Картинка хранится файлом,
в БД — ссылка и результаты. При ошибке модели — лог worker, без готовой записи БД.

Пользователь может дополнительно выбрать папку **на своём компьютере** в браузере
и по кнопке сохранить туда копию четырёх файлов после инференса. Без выбранной папки
или поддержки File System Access API доступен ZIP. Основная копия в volume остаётся
в обоих случаях. Серверная папка для дополнительной копии не нужна. Браузер не
опрашивает состояние: сохранение запрашивается вручную; до появления комплекта 404.

Три постоянных процесса, зависимость детектор → классификатор, lock, проверки памяти и crop padding
10% сохранены. Исходные ответы моделей и raw_caption не заменяются производными;
семантика COCO/ImageNet в простой версии не вычисляется. Новая миграция только
добавляет processed_images; прежние таблицы/данные и миграции не удалять. Перед
обновлением завершить старую очередь прежним worker (job_id заменён на image_id).
Дубликат UUID пропускает инференс, при готовых файлах после сбоя БД повторяется
только commit. Восстановление отдельных этапов удалено. Реальные модели/сравнения
в этой переделке не запускать; CPU/mock и настоящую инфраструктурную интеграцию
отмечать отдельно. Подробные актуальные команды — README.md.
