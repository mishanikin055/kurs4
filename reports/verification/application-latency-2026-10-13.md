# Разбор задержки ответа приложения — 13.10.2026

Проверка по запросу пользователя: почему приложение отвечает значительно дольше,
чем можно ожидать по результатам сравнений. Код приложения не изменялся;
новые модельные прогоны, загрузки изображений и benchmarks не выполнялись.

## Проверенные факты

- Изучены текущие адаптеры, обработчик задания, настройки worker, frontend
  и скрипты сравнений.
- Прочитаны существующие логи Celery, статусы и времена заданий PostgreSQL,
  метаданные сохранённых PNG и сохранённые CSV сравнений.
- SHA-256 `backend/models.py` и `backend/processing.py` внутри работающего worker
  совпадают с файлами рабочей копии.
- Фактическая настройка worker: `device=cuda`. Адаптеры явно используют этот
  device; автоматического перехода на CPU в них нет.
- В момент проверки у worker нет событий cgroup OOM, достижения лимита памяти
  или ограничения CPU quota. Это не измерение нагрузки во время инференса.

В `scripts/detection/common.py:458` модель создаётся до цикла изображений,
время загрузки записывается отдельно как `cold_load_ms`, затем выполняется прогрев.
В `scripts/detection/common.py:328` измеряется обработка уже загруженной модели.

## Причины в текущем коде

1. **Три холодных модельных процесса на каждое изображение.**
   `backend/processing.py:79–108` запускает отдельный Python для каждого этапа
   и ждёт его завершения. `backend/models.py:28`, `:83`, `:123` каждый раз
   создают RF-DETR, ViT и Florence соответственно. Повторяются импорты ML-библиотек,
   инициализация CUDA и загрузка весов. Постоянный контейнер Celery этого не отменяет.
   Это соответствует текущему требованию о завершении модельного процесса
   перед следующим этапом, но увеличивает задержку одиночного запроса.

2. **Полное чтение и хеширование весов перед каждым этапом.**
   `backend/models.py:13–25`, вызов `:166`: проверяются все файлы checkpoint,
   затем адаптер отдельно загружает веса. Три каталога моделей занимают суммарно
   около 1.12 GiB. Даже при файловом кэше повторяется SHA-256 и обращение к данным.
   Точный вклад этой проверки сейчас не измеряется.

3. **Полный ответ включает три последовательных этапа.**
   Детектор обрабатывает изображение один раз, ViT — каждый объект отдельно
   (`backend/models.py:98–119`), Florence генерирует описание (`:148–154`).
   Время детектора из сравнительной таблицы не описывает весь запрос приложения.
   При большом количестве объектов добавится время классификации каждой вырезки.

4. **Есть дополнительные ожидания доставки и отображения.**
   `backend/settings.py:15`: publisher interval по умолчанию 2 секунды.
   `frontend/app.js:138`: повторный опрос через 2 секунды после завершения
   предыдущего опроса. Это добавляет задержку до старта и до показа готового
   результата, но не объясняет 23–26 секунд внутри обработчика.
   UI уже получает PNG при `image_ready`, до завершения аннотирования.

5. **Недостаточно измерений для точного распределения времени.**
   Обработчик не сохраняет замеры этапов, а stdout/stderr модельных процессов
   направлены в DEVNULL (`backend/processing.py:95–96`). По существующим данным
   нельзя разделить оставшиеся 12 секунд между ViT, Florence, импортами и I/O.

## Следующие изменения по приоритету

1. Добавить небольшие замеры в технический лог: проверка checkpoint, загрузка
   модели, инференс, полная длительность процесса. Компактную схему БД не менять.
2. Убрать повторную полную проверку неизменных весов из каждого задания:
   проверять до обработки очереди при запуске worker, явно сохранив проверку
   соответствия checkpoint и условия повторной проверки при смене файлов.
3. После измерений оптимизировать самый дорогой участок запуска/загрузки.
   Для скорости, близкой к прогретому benchmark, потребуется повторное использование
   загруженных моделей; это требует пересмотра текущего жизненного цикла процессов
   и проверки RAM/VRAM. Одновременное удержание трёх моделей противоречит текущим
   требованиям и здесь не предлагается как готовая безопасная правка.
4. Сокращение интервалов publisher/UI улучшит отзывчивость, но не устранит
   время загрузки моделей.

## Ограничения проверки

Новые модели не запускались; отдельные времена импорта, SHA-256, загрузки,
инференса и завершения процессов не измерялись. Основное объяснение задержки
подтверждается кодом и существующими временами заданий, но точная доля каждого
участка требует инструментированного запуска по отдельной задаче пользователя.
