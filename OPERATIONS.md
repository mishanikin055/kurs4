# Техническая документация Image Analysis

Версия 0.3.5. Запуск — в [README](README.md). Старые учебные материалы находятся в archive/coursework.

## Компоненты и хранение

Docker поднимает nginx frontend, FastAPI backend, Elasticsearch, RabbitMQ и Celery worker. S3 по умолчанию — локальный MinIO; при внешнем endpoint локальный сервер не запускается. API модели не загружает. Очередь содержит только UUID; worker concurrency/prefetch/batch = 1. Elasticsearch и локальный S3 не публикуют порты на хост; API/frontend доступны через localhost.

API проверяет JPEG/PNG, применяет EXIF orientation и создаёт RGB PNG без EXIF. Исходные байты не записываются в постоянное хранилище. Для передачи между API и worker нормализованный PNG временно лежит в volume `pending_inputs`; метаданные входа — в Elasticsearch. После этого API отправляет UUID с подтверждением RabbitMQ. Потерянное подтверждение может означать доставленное сообщение, поэтому временный вход сохраняется для повтора.

RF-DETR Small выполняет детекцию параллельно с описанием сцены Florence-2-base-ft. Затем тот же Florence последовательно описывает вырезки с padding 10%; bbox и COCO label остаются исходными. Классификация здесь — описание объектов, без ViT, определения цвета или выдуманных структурированных атрибутов. В том же процессе Florence локальная модель OPUS-MT TC Big (`Helsinki-NLP/opus-mt-tc-big-en-zle`) переводит описания сцены и объектов на CPU. Исходные `raw_caption`/`object_caption` сохраняются дословно; перевод записывается отдельно в `russian_caption` и показывается в интерфейсе. Переводчик не обращается к внешним API при обработке. Его файлы скачиваются вместе с остальными моделями; веса переводчика занимают около 0,48 ГБ на диске и около 0,96 ГБ RAM в FP32, дополнительно нужна память для вычислений. Это размеры весов, а не полное потребление процесса. Для русского выбирается языковой токен `>>rus<<`, декодирование использует beam search с четырьмя вариантами. Старые готовые UUID автоматически не переводятся.

В S3 постоянно сохраняются **вырезки PNG и общее изображение `detection.png` с рамками bbox и COCO-подписями**. При отсутствии объектов сохраняется нормализованная сцена без рамок. Elasticsearch хранит UUID, размеры, дату, исходные ответы аннотации/классификации/детекции, список вырезок и S3 keys/размеры/SHA256 всех PNG. Ссылки остаются в существующем поле `crop_files`, включая `detection.png`, поэтому изменение mapping и перенос индекса не нужны. Поле manifest `detection_image` обозначает наличие общей картинки у новых результатов. В индексе нет изображений, base64 или оригинальных байтов. `results.json` формируется из manifest по запросу, в S3 не записывается. Mapping сохраняет описания как text, COCO label/object_id как keyword, коллекции объектов как nested. Интерфейс поиска пока отсутствует.

После всех вычислений worker загружает вырезки и общее изображение, затем одной условной записью публикует полный ES-документ. До этой записи результат недоступен. Используются `_seq_no`/`_primary_term`, чтобы повторная доставка не перезаписала готовый результат ([документация Elasticsearch](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/optimistic-concurrency-control)). Готовый UUID не пересчитывается. После публикации временный вход удаляется; повторная доставка также завершает удаление, если процесс прервался после записи ES.

Модельные subprocess не импортируют клиенты хранилища. Для них ограничено число malloc arenas и включён ранний возврат освобождённых CPU-буферов загрузки моделей; пороги RAM/VRAM остаются действующими ([параметры glibc](https://sourceware.org/glibc/manual/latest/html_node/Malloc-Tunable-Parameters.html)).

Общей транзакции ES/S3/RabbitMQ нет. Сбой S3 или ES может оставить PNG без ссылки; неоднозначное подтверждение ES не даёт безопасно удалить их сразу. Автоматической очистки таких файлов и reconciliation необработанных входов нет. При ошибке нормализованный вход сохраняется, поскольку нужен для повтора; при повторной попытке возможен новый инференс. Exactly-once не обещается. Общий inference-lock и временный scratch моделей сохранены.

## HTTP API

| Метод и путь | Результат |
|---|---|
| `POST /images` | Multipart `file`; `202 {"image_id":"UUID"}` после сохранения временного входа/метаданных и подтверждения брокера. |
| `GET /images/{id}` | Готовый manifest, `404` до готовности. |
| `GET /images/{id}/files/results.json` | JSON из Elasticsearch. |
| `GET /images/{id}/files/crops/{object_id}.png` | Вырезка из S3 с проверкой размера/SHA256. |
| `GET /images/{id}/files/detection.png` | Общее изображение с bbox из S3 с проверкой размера/SHA256; для результатов до 0.3.3 — 404. |
| `GET /images/{id}/archive` | ZIP: `results.json`, `detection.png` и `crops/`; исходник в него не входит. |
| `GET /health` | Готовность RabbitMQ, Elasticsearch index и S3 bucket; не качество моделей. |

Исходник и `normalized.png` после обработки по API недоступны. `detection.png` новых заданий хранится в S3 и доступен отдельно, в ZIP и при сохранении в выбранную папку. Старые результаты без него продолжают скачиваться; их повторный инференс не запускается. Браузер держит локальный preview выбранного файла в текущей вкладке; применяет EXIF orientation и проверяет размеры перед наложением bbox. При невозможности preview JSON и вырезки остаются доступны. Новый выбор файла во время ожидания не подменяет preview уже отправленного изображения. Двухколоночная компоновка и выделение всех bbox сохранены.

Ошибки загрузки: 413 — лимит, 415 — формат, 422 — некорректное изображение. Недоступность хранилищ/брокера — 503 без внутренних параметров. Браузер автоматически ждёт результат; отдельного endpoint статуса нет, ошибки модели видны в worker logs.

## Подключение S3

### Локальный MinIO

Для новой установки оставьте `.secrets/app.env` отсутствующим и запустите launcher по README. Он создаст файл с локальными случайными паролями. Пустой/не заданный `APP_S3_ENDPOINT_URL` или `http://s3:9000` выбирает локальный MinIO. `s3` — имя сервиса внутри сети Compose; порты MinIO на хост не публикуются.

Локальные `APP_S3_ACCESS_KEY`/`APP_S3_SECRET_KEY` должны совпадать с `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`. Не меняйте случайно сгенерированные пароли при повторном запуске: существующие настройки launcher сохраняет. `.secrets/app.env` применяется через Compose `env_file`; shell-переменные `APP_S3_*` сами по себе его значения не заменяют.

### Внешний S3

1. Создайте **закрытый bucket** у провайдера и отдельные ключи для приложения. Публичный доступ и браузерный CORS не нужны: вырезки читает backend и отдаёт браузеру через API. Авторизации приложения пока нет, поэтому оставьте frontend/API доступными только локально.
2. Выдайте ключам право проверки bucket (`HEAD Bucket`, в AWS — `s3:ListBucket` на bucket), записи `s3:PutObject` и чтения `s3:GetObject` для объектов этого bucket. Сопоставление прав у других провайдеров может отличаться. Если bucket отсутствует, инициализация пробует создать его; тогда потребуется и право создания bucket. Проще подготовить bucket заранее. Удаление объектов текущему runtime не требуется.
3. Откройте `.secrets/app.env` в редакторе. При новой установке создайте папку `.secrets` и файл `app.env`. Добавьте или замените **только пять строк** ниже; каждая переменная должна встретиться один раз. Сохраните остальные строки, особенно настройки RabbitMQ, Elasticsearch и локальные `MINIO_*`. Не выполняйте копирование `backend/app.env.example` поверх действующего файла.

```dotenv
APP_S3_ENDPOINT_URL=https://s3.example.com
APP_S3_ACCESS_KEY=YOUR_ACCESS_KEY
APP_S3_SECRET_KEY=YOUR_SECRET_KEY
APP_S3_BUCKET=my-image-crops
APP_S3_REGION=us-east-1
```

Используйте endpoint **S3 API**, без имени bucket, имени объекта и credentials в URL. Регион, endpoint и ключи возьмите у своего провайдера; примеры не являются рабочими настройками. Файл — секрет, он исключён из Git. Для значений с `$` или `#` используйте одинарные кавычки dotenv, например `APP_S3_SECRET_KEY='value-with-$-and-#'`: Compose иначе может интерпретировать подстановку или комментарий. Не вставляйте ключи в команды или публичные логи.

4. Проверьте сетевой адрес с учётом Docker:

- Публичное DNS-имя должно разрешаться из контейнеров; прокси, firewall и VPN должны пропускать их трафик.
- `localhost`/`127.0.0.1` в endpoint указывают на сам контейнер backend/worker, а не на компьютер или другой контейнер. Для S3 на хосте Docker Desktop обычно используется `host.docker.internal`; в Linux Docker Engine такое имя не настроено этой поставкой, нужен доступный контейнерам адрес/настройка Docker. S3 на хосте должен слушать доступный интерфейс.
- Клиент использует **path addressing**: провайдер должен поддерживать запросы вида `endpoint/bucket/key`. Для внешнего хранилища используйте HTTPS с доверенным сертификатом и совпадающим DNS-именем. HTTP не шифрует трафик. Проверка TLS включена; отдельной настройки собственного CA и session token в шаблоне приложения нет. Для провайдера с обязательными временными ключами/session token эта конфигурация не подходит без доработки.

5. Запустите проверку, затем приложение с выбранным устройством:

```bash
python3 scripts/start_app.py --device cpu --check
python3 scripts/start_app.py --device cpu
```

На Windows замените `python3` на `py -3`; для GPU используйте свой режим из README. `--check` проверяет настройки и веса, **не соединение с S3**. Обычный запуск проверяет bucket через `HEAD` перед запуском нового worker. Отсутствующий bucket создаётся только при ответе `404`/`NoSuchBucket`; ошибка доступа не превращается в создание bucket. `HEAD` не доказывает права PUT/GET: полный цикл записи/чтения проверяется при обработке и скачивании результата. Реальный внешний облачный провайдер пока не проверен.

Launcher автоматически добавляет `compose.app.external-s3.yaml`: MinIO не собирается/не запускается, зависимости API/worker от него удаляются через `!reset`. Требуется современный Docker Compose с поддержкой этого тега. После успешной инициализации внешнего хранилища и переключения приложения прежний локальный MinIO останавливается, volume сохраняется. Новые ключи провайдера launcher не генерирует. Неполные настройки или недоступный внешний S3 останавливают запуск; локального fallback нет. Уже работающие сервисы не откатываются и не останавливаются автоматически при любой ошибке запуска.

### Смена хранилища

1. Дождитесь результата текущего изображения, убедитесь, что нет ожидающей обработки, затем остановите сервисы командой `stop` из раздела диагностики. Прерывание обработки сохраняет нормализованный вход для повтора; не удаляйте очередь и `pending_inputs`.
2. Сохраните прежние настройки в защищённом месте. Согласованная резервная копия приложения должна учитывать ES, S3, очередь/временные входы и секреты. Настройки сами по себе не являются копией данных.
3. Измените пять настроек S3, сохранив остальные строки файла, и запустите прежнюю команду launcher. Для возврата к локальному MinIO установите `APP_S3_ENDPOINT_URL=http://s3:9000` и восстановите `APP_S3_ACCESS_KEY`/`APP_S3_SECRET_KEY` из прежних `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`, а также прежние bucket/region.

Смена endpoint или bucket **не переносит сохранённые PNG**. ES хранит ключи объектов, но не прежний endpoint/bucket: старые результаты после переключения ищут вырезки и общее изображение в новом месте. Для доступа к ним нужно заранее скопировать объекты с сохранением ключей и байтов либо вернуть прежние настройки. Простая смена имени bucket данные не перемещает. Launcher не удаляет старые ES/S3 данные и не выполняет их перенос.

## Остальные настройки и запуск

| Переменная | Назначение |
|---|---|
| `APP_ELASTICSEARCH_URL` | `http://elasticsearch:9200` внутри Docker. |
| `APP_ELASTICSEARCH_INDEX` | `image-results`. |
| `APP_S3_ENDPOINT_URL` | Пустой/`http://s3:9000` — локальный MinIO; другой HTTP(S)-адрес — внешний S3. |
| `APP_S3_ACCESS_KEY`, `APP_S3_SECRET_KEY` | Локально совпадают с `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`; для внешнего S3 — ключи провайдера. |
| `APP_S3_BUCKET`, `APP_S3_REGION` | Локально `image-analysis`, `us-east-1`; для внешнего S3 задаются явно. |
| `APP_PENDING_INPUT_DIR` | `/var/lib/kurs4/pending`, общий временный вход API/worker. |
| `APP_BROKER_URL` | URL RabbitMQ из секретов. |
| `APP_DEVICE` | Явный `cpu`/`cuda`; launcher выбирает режим. |
| `APP_MAX_UPLOAD_BYTES`, `APP_MAX_IMAGE_PIXELS` | 10 МиБ, 25 000 000. |
| `APP_MAX_ARTIFACT_BYTES`, `APP_MAX_BUNDLE_BYTES` | 128 МиБ, 256 МиБ. |
| `APP_STAGE_TIMEOUT`, `APP_JOB_TIMEOUT` | 600 и 2400 секунд. |

Порты `APP_FRONTEND_PORT`/`APP_HTTP_PORT` (8080/8000) и `APP_WORKER_MEMORY` задаются в окружении Compose. Остальные `APP_*` — в `.secrets/app.env`. ES использует heap 512 МиБ и лимит контейнера 1 ГБ; это локальная single-node конфигурация. Linux x86_64, CPU и NVIDIA CUDA остаются явными режимами. Реальный CPU-инференс не проверялся; проверку CUDA см. в конце документа.

MinIO собирается из закреплённого upstream release в `docker/minio.Dockerfile`, лицензия включена в образ. Первой сборке нужен интернет для Go-зависимостей. Отдельный MinIO контейнер имеет постоянный volume `s3data`; Elasticsearch — `esdata`. Модели и секреты не входят в образы/архив Git.

Инициализация существующего локального окружения без запуска моделей:

```bash
docker compose -p kurs4-app -f compose.app.yaml build s3 backend frontend
docker compose -p kurs4-app -f compose.app.yaml up -d --wait elasticsearch s3 rabbitmq
docker compose -p kurs4-app -f compose.app.yaml run --rm --no-deps backend python -m backend.db
docker compose -p kurs4-app -f compose.app.yaml up -d backend frontend
```

Обычный запуск с обработкой — `python3 scripts/start_app.py --device cpu` (либо `cuda`). Режим `cuda` требует зарегистрированного NVIDIA runtime Docker и проверяется до сборки. Если локальный Docker Engine запущен прямо в WSL без этого runtime, используйте `python3 scripts/start_app.py --device wsl-cuda`: отдельный override передаёт `/dev/dxg` и библиотеки WSL, сохраняя `APP_DEVICE=cuda`. CPU автоматически не подставляется. Настройка стандартного NVIDIA runtime описана в [документации NVIDIA](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).

`MemoryError: Less than 768 MiB host RAM available` означает нехватку доступной RAM WSL/хоста во время загрузки моделей. Защиту не отключайте: освободите память или увеличьте лимит WSL. После такой ошибки worker освобождает частично загруженные модели и ждёт 30 секунд до новой попытки, не забирая задания из очереди. Heap Elasticsearch ограничен 512 МиБ, чтобы оставить больше памяти двум модельным процессам; это не отменяет общего требования к ресурсам.

## Работа без интернета

Первая установка скачивает образы, зависимости и закреплённые веса. После неё основной интерфейс, API, документация Swagger, модели и локальное хранилище работают без внешней сети. CSS/JS Swagger включены в frontend, внешний validator отключён. Модельные процессы используют только локальные файлы; OPUS-MT TC Big выполняет перевод на CPU, в FP32, без выделения VRAM. Для внешнего S3 необходима доступность его endpoint.

Для запуска ранее созданных и остановленных контейнеров без сборки и скачивания используйте `docker compose -p kurs4-app -f compose.app.yaml --profile processing start`. Это сохраняет устройство и mounts из первоначального запуска. `start` не создаёт удалённые контейнеры; после `down` необходимо повторное создание. Не удаляйте образы, веса и volumes, если планируете работать без сети.

## Остановка и диагностика

Команды выполняются из папки проекта. Логи и состояние можно смотреть без запуска моделей или обработки нового изображения:

```bash
docker compose -p kurs4-app -f compose.app.yaml --profile processing ps -a
docker compose -p kurs4-app -f compose.app.yaml --profile processing logs --tail 100 backend worker
docker compose -p kurs4-app -f compose.app.yaml logs --tail 100 elasticsearch rabbitmq
curl --fail http://localhost:8080/api/health
```

В PowerShell используйте `curl.exe`. Успешная проверка возвращает HTTP 200 и `{"rabbitmq":true,"elasticsearch":true,"s3":true}`. HTTP 503 и `false` указывают на недоступную зависимость. Это проверка соединения с bucket, индексом и брокером; готовность моделей смотрите в worker logs (сообщения `Resident model ready`). Если HTTP недоступен, сначала проверьте `ps` и логи backend/frontend. При своих портах замените 8080.

При ошибке S3 проверьте пять строк настроек, endpoint S3 API, DNS/доступ из Docker, регион, права `HEAD` и сертификат. Не публикуйте полный `.secrets/app.env` или вывод `docker compose config`: он может содержать секреты. Логи перед передачей также просмотрите на наличие закрытых данных.

Дождитесь окончания текущей обработки и остановите приложение:

```bash
docker compose -p kurs4-app -f compose.app.yaml --profile processing stop
```

`stop` сохраняет контейнеры, сеть и volumes. Если требуется удалить контейнеры и сеть, используйте `down` **без `-v`**:

```bash
docker compose -p kurs4-app -f compose.app.yaml --profile processing down
```

Эти команды не запускают сервисы; для состояния/остановки базового Compose достаточно и после запуска с GPU или внешним S3. Для запуска используйте launcher с прежним `--device`: он выберет нужные override-файлы. Не используйте `down -v`, очистку volumes или удаление данных ES/S3 при обычной остановке/обновлении. При внешнем S3 остановка Docker не удаляет bucket провайдера.

## Структура проекта

| Путь | Назначение |
|---|---|
| `backend/`, `frontend/` | API/worker и браузерный интерфейс; текущий runtime Elasticsearch/S3. |
| `scripts/` | Загрузка закреплённых моделей и launcher приложения. |
| `compose.app.yaml`, `compose.app.*.yaml`, `docker/` | Текущая сборка приложения и override для GPU/внешнего S3. |
| `compose.yaml` | Прежнее окружение сравнительных экспериментов; для запуска приложения не требуется. |
| `detection/`, `annotation/`, `classification/` | Модельные исходники и manifests; приложение использует RF-DETR и Florence, а не сравнительные модели. |
| `.secrets/` | Локальные секреты; не публиковать и не добавлять в Git. |
| `storage/`, `data/`, локальные каталоги весов | Локальные данные, блокировки и тяжёлые файлы; не очищать как «мусор». |
| `archive/coursework/`, `Материалы для курсовой/` | Сохранённые учебные/научные материалы, прежние отчёты и DOCX; остаются в репозитории/рабочем каталоге, в чистый архив приложения не входят. |

Служебные кэши Python/pytest/Ruff можно восстановить; данные Docker volumes, веса, секреты и исторические материалы к таким кэшам не относятся. Публичное многопользовательское развёртывание не входит в поставку.

## Переход с PostgreSQL

Пользователь разрешил начать с пустой базы и удалить старую PostgreSQL без дампа/переноса. Перед переходом остановите прежние backend/worker; старые UUID очереди относятся к прежнему хранилищу и должны быть удалены из очереди `inference`, если они есть. Создайте настройки Elasticsearch/S3 по `backend/app.env.example`, сохранив действующие настройки RabbitMQ. Launcher дополняет старый файл отсутствующими настройками нового хранилища без замены существующих паролей.

Сервис `db` и volume `pgdata` больше не используются Compose. Удалены неиспользуемый SQL-импорт, старые интеграционные тесты worker и контроллер остановки PostgreSQL. Таблицы/миграции и тест миграций оставлены на месте, чтобы сохранить уже имевшиеся локальные пользовательские изменения; текущий runtime их не импортирует, SQL-зависимости из сборки удалены. Тест старых миграций исключён из текущего pytest, остатки SQL не входят в Docker-сборку и чистый ZIP. Команды Alembic к новой системе не применимы.

.venv-backend/bin/python -m ruff check --no-cache .

`APP_TEST_INTEGRATION=1` включает тесты настоящих Elasticsearch/S3. Используйте отдельные тестовые контейнеры и тестовые credentials: тест создаёт и удаляет только свои случайные index/bucket. Инференс в нём синтетический, веса не загружаются. Новые отчёты, benchmark и проверки производительности без отдельного поручения не создаются.
