# Техническая документация Image Analysis

Документ относится к версии 0.2.0. Начало работы — в [README](README.md). Старые планы, исследования и отчёты находятся в [архиве](archive/coursework/INDEX.md) и не задают текущую архитектуру.

## Компоненты и обработка

Пять контейнеров: nginx frontend, FastAPI backend, PostgreSQL, RabbitMQ и Celery worker. Frontend проксирует `/api/` и не получает секреты/модели. API принимает и валидирует изображения, сохраняет исходные байты и нормализованный PNG в БД, затем публикует UUID в RabbitMQ с подтверждением доставки. Модели в API не загружаются.

Worker обрабатывает одно изображение одновременно. Постоянные отдельные процессы держат RF-DETR Small и Florence-2-base-ft. Детекция и `<DETAILED_CAPTION>` сцены выполняются параллельно. Затем тот же Florence последовательно описывает все вырезки с `<CAPTION>`. Вырезки расширены на 10% с каждой стороны в пределах изображения; bbox остаётся исходным. Вся вырезка поступает штатному процессору. ViT и обучение в приложении отсутствуют.

После всех успешных этапов одна транзакция записывает артефакты, строки объектов и manifest готового результата. До commit результат недоступен. Исходные `object_caption` и `raw_caption` сохраняются без переписывания. Преобразования текста в браузере относятся только к отображению. Общий inference-lock защищает приложение и научные запуски от конкуренции за память.

Постоянного файлового медиахранилища больше нет. Модели и lock остаются файлами; это не пользовательский архив. Для существующих модельных адаптеров worker кратковременно материализует изображение в TemporaryDirectory. Compose монтирует `/tmp` как tmpfs до 1 ГБ. Полный запрет любых временных файлов не заявляется: multipart/parser, IPC и модельные библиотеки также используют временные данные.

## Схема хранения и будущий поиск

| Таблица | Назначение |
|---|---|
| `image_records` | UUID, размеры, время добавления; `manifest` SQL NULL до готовности, JSONB после commit. |
| `image_artifacts` | `(image_id, filename)` и `BYTEA` исходника/PNG/JSON/вырезок, тип содержимого. |
| `image_objects` | `(image_id, object_id)`, COCO label, bbox, исходное описание, JSONB attributes. |
| `processed_images` | Прежняя таблица ссылок; сохранена для совместимости/переноса, новые результаты туда не пишутся. |
| `alembic_version` | Версия схемы. |

Фотографии отделены от каталога: SQL-запросы к объектам не читают BYTEA. Составной индекс `(label, image_id)` ускоряет выборку классов, GIN по `attributes` подготовлен для будущих структурированных атрибутов. Поле `attributes` сейчас пустое; цвет и embeddings не вычисляются. Метаданные описания не являются доказательством цвета или подтипа по пикселям.

Пример запроса без бинарных данных:

```sql
SELECT o.image_id, o.object_id, o.bbox, o.object_caption
FROM image_objects AS o
JOIN image_records AS i ON i.id = o.image_id
WHERE o.label = 'car' AND i.manifest IS NOT NULL;
```

Будущий фильтр цвета должен относиться к **той же строке объекта**, что и класс. Например, `o.attributes @> '{"color":"red"}'` будет иметь смысл только после реализации и проверки заполнения атрибутов. Сейчас такой запрос не вернёт распознанные красные машины.

PostgreSQL выбран для локального продукта ради транзакций и сохранения существующего стека. Терабайт — объём архива, а не размер одной записи: BYTEA ограничено размером отдельного значения, не всей БД. Практическая производительность терабайтного каталога не измерена. По мере роста потребуются расчёт диска/WAL/backup, настройка памяти, измерения на реальном распределении данных и планирование времени восстановления; само наличие индекса не даёт обещания скорости.

Источники ограничений: [PostgreSQL Large Objects и TOAST](https://www.postgresql.org/docs/current/lo-intro.html), [MongoDB GridFS и отсутствие транзакций комплекта](https://www.mongodb.com/docs/manual/core/gridfs/). GridFS рассматривался, но смена СУБД для текущих фотографий не обоснована измерениями.

## HTTP API

| Метод и путь | Результат |
|---|---|
| `POST /images` | Multipart `file`; `202 {"image_id":"UUID"}` только после DB commit и подтверждения брокера. |
| `GET /images/{id}` | Готовый manifest; `404` до готовности. |
| `GET /images/{id}/files/{filename}` | Байты `original`, `normalized.png`, `detection.png`, `results.json`, `crops/<UUID>.png` из БД. |
| `GET /images/{id}/archive` | ZIP одного ограниченного по размеру комплекта, создаётся по запросу. |
| `GET /health` | Проверка доступности компонентов API; не проверка качества инференса. |

Ошибки изображения: `413` превышение лимита, `415` неподдерживаемый формат, `422` некорректные данные. Недоступность БД/брокера — `503`. Нет таблиц заданий, endpoint статуса или callback. Браузер повторяет GET после `404` через две секунды, максимум 40 минут; отдельный запрос ограничен 15 секундами. Ошибку инференса смотрят в worker logs; по отсутствующему manifest нельзя отличить ожидание от ошибки модели.

API/скачивание сохраняют исходные ответы; GET добавляет legacy ImageNet-уточнение только старым результатам, браузер не выдаёт его за описание. Legacy-комплекты без вырезок допускаются при импорте. Пустой новый набор объектов даёт пустую папку crops в ZIP.

## Ошибки, очередь и повторная доставка

RabbitMQ получает только UUID. Потерянное подтверждение отправки может означать доставленное сообщение: входные байты в БД не удаляются. Между PostgreSQL и RabbitMQ нет общей транзакции. Авария после сохранения входа, но до публикации может оставить необработанный вход; автоматического outbox/reconciliation нет. Повторный POST создаёт новый UUID. Нельзя обещать exactly-once.

Worker подтверждает успешную задачу после commit. Повторная доставка готового UUID не запускает модели и не переписывает комплект. При отказе commit после инференса временные файлы удаляются, manifest остаётся неготовым; после восстановления задача может вычислиться заново. При модельной ошибке готовый комплект не публикуется, исходные входы остаются в БД. При потере процесса/IPC worker перезапускается, чтобы следующий запрос не получил старый ответ.

Входы без manifest можно проверить вручную:

```sql
SELECT id, created_at FROM image_records WHERE manifest IS NULL ORDER BY created_at;
```

Не удаляйте такие записи только по возрасту: сообщение могло быть доставлено или ещё находиться в очереди.

## Настройки и переносимость

Секреты генерирует launcher из `backend/app.env.example`. Существующий `.secrets/app.env` не заменяется. Настройки БД/брокера должны совпадать с контейнерами. Не публикуйте этот файл.

| Настройка | Значение по умолчанию / назначение |
|---|---|
| `APP_DATABASE_URL` | PostgreSQL SQLAlchemy URL из секретов. |
| `APP_BROKER_URL` | RabbitMQ URL из секретов. |
| `APP_DEVICE` | Launcher задаёт `cpu` либо `cuda`. |
| `APP_WORKER_MEMORY` | Compose memory limit: launcher CPU 8g, CUDA 5g. Задаётся во внешнем окружении перед запуском. |
| `APP_FRONTEND_PORT`, `APP_HTTP_PORT` | 8080 и 8000, привязка к localhost. |
| `APP_MAX_UPLOAD_BYTES` | 10 МиБ. |
| `APP_MAX_IMAGE_PIXELS` | 25 000 000. |
| `APP_MAX_ARTIFACT_BYTES` | 128 МиБ, меньше предела BYTEA. |
| `APP_MAX_BUNDLE_BYTES` | 256 МиБ; влияет на RAM формирования ZIP. |
| `APP_STAGE_TIMEOUT`, `APP_JOB_TIMEOUT` | 600 и 2400 секунд. |

Параметры `APP_*` приложения добавляйте в `.secrets/app.env`; переменные подстановки Compose (порты, worker memory) задавайте в окружении терминала. При увеличении лимитов бинарников нужно одновременно пересчитать память API/worker/tmpfs.

Стандартный NVIDIA запуск использует `compose.app.gpu.yaml`, [GPU reservation Docker](https://docs.docker.com/compose/how-tos/gpu-support/). Старый прямой доступ WSL вынесен в `compose.app.wsl-gpu.yaml` и доступен через `--device wsl-cuda`; он нужен только для такой конкретной установки. На обычном Linux этих путей нет и они не используются. ARM, Apple GPU и произвольные CUDA-драйверы не поддерживаются обещанием «любой компьютер».

Приложение рассчитано на один компьютер. Порты публикуются на localhost; перед доступом из интернета требуется отдельное проектирование авторизации/TLS/ограничений загрузок. Сейчас публичное многопользовательское развёртывание не входит в поставку.

## Backup и обновление

Обычная остановка не удаляет volumes. Backup должен включать PostgreSQL (теперь и фотографии), настройки секретов и закреплённые веса либо способ их восстановления. RabbitMQ volume нужен для незавершённой очереди. Для согласованного обслуживания прекратите загрузки и завершите очередь прежним worker, затем остановите backend/worker. Не меняйте формат заданий на непустой очереди.

Дамп через установленный Python, без shell-перенаправления бинарного потока PowerShell:

```python
# Запустить из папки проекта: python3 backup.py, предварительно сохранив этот пример.
import subprocess
from pathlib import Path

command = [
    "docker",
    "compose",
    "-p",
    "kurs4-app",
    "-f",
    "compose.app.yaml",
    "exec",
    "-T",
    "db",
    "sh",
    "-c",
    'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc',
]
with Path("image-analysis.dump").open("xb") as stream:
    subprocess.run(command, stdout=stream, check=True)
```

Не сохраняйте дамп в Git. Проверяйте восстановление в отдельную тестовую БД через `pg_restore`, прежде чем рассчитывать на резервную копию. В рабочей БД этого сеанса миграции и импорт автоматически не выполняются.

После резервной копии и проверки нужной ревизии ручное применение миграций:

```bash
docker compose -p kurs4-app -f compose.app.yaml run --rm backend alembic -c backend/alembic.ini upgrade head
```

Новая миграция добавляет таблицы медиахранилища и не удаляет legacy-таблицу. Старые миграции сохранены; среди них есть прежнее удаление таблиц заданий, поэтому launcher не применяет цепочку к старой/неизвестной схеме без ручного обслуживания.

Импорт старых файлов выполняется отдельной командой после миграции, без моделей; команда — `python -m backend.import_legacy /legacy/results`. Для прежнего стандартного volume сначала проверьте его наличие, затем запустите импорт:

```bash
docker volume inspect kurs4-app_image_data
docker compose -p kurs4-app -f compose.app.yaml run --rm --no-deps -v kurs4-app_image_data:/legacy:ro backend python -m backend.import_legacy /legacy/results
```

Не запускайте вторую команду, если проверка volume завершилась ошибкой: Docker иначе создаст пустой volume с таким именем. Для другой установки подставьте настоящее имя старого volume или абсолютный путь каталога. Каталог источника монтируется только для чтения. Импорт должен сохранить UUID, исходные байты и JSON; конфликтующие или неполные комплекты не перезаписываются. Старый image volume и legacy БД удалять нельзя до проверки импорта, контрольных сумм и backup restore. Повторный импорт не должен порождать дубли.

## Разработка, проверки и выпуск

Код: `backend/` — API/service/repository, pipeline и runtime; `frontend/` — статический интерфейс; `scripts/start_app.py` — запуск; `scripts/fetch_app_models.py` — подготовка двух моделей. Исследовательский код сохранён в detection/classification/annotation, но не является частью обычного запуска.

```bash
python3 -m venv .venv-backend
.venv-backend/bin/python -m pip install -r backend/requirements-dev.txt
.venv-backend/bin/python -m pytest -q backend/tests
.venv-backend/bin/python -m ruff check --no-cache .
.venv-backend/bin/python -m ruff format --check --no-cache .
```

На Windows используйте `py -3 -m venv .venv-backend` и `.venv-backend/Scripts/python.exe`. Полный pytest научных модулей требует дополнительных ML/metric зависимостей. Интеграционные тесты включаются только `APP_TEST_INTEGRATION=1` с отдельными PostgreSQL/RabbitMQ: они очищают тестовую очередь. Нельзя направлять их на рабочую БД/очередь.

Версия API находится в `backend/__init__.py`, теги образов — в `compose.app.yaml`, история — в [CHANGELOG](CHANGELOG.md). Обновляйте их вместе. ZIP исходников формируется из проверенного Git commit, например `git archive --format=zip --prefix=image-analysis/ --output=image-analysis.zip HEAD`. В нём нет весов, секретов и локальных тяжёлых результатов. Исходные лицензии стороннего кода сохраняются. Реальные model smoke, нагрузочный терабайтный тест и mock-тесты следует указывать раздельно.
