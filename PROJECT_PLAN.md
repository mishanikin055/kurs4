# План проекта: простая обработка изображений

Актуальное уточнение пользователя от 19.10.2026 заменяет прежнюю схему заданий,
статусов и публикации через БД. Научные сравнения, веса и исходные материалы не меняются.

## Поток

```mermaid
flowchart LR
    U[Браузер] -->|Загрузка| F[nginx frontend]
    F --> API[FastAPI]
    API -->|Оригинал и RGB PNG| V[(image_data volume)]
    API -->|image_id| Q[RabbitMQ]
    Q --> W[Celery worker]
    W --> D[RF-DETR Small]
    W --> A[Florence-2: сцена DETAILED_CAPTION]
    D --> C[Ожидание рамок и завершения сцены]
    A --> C
    C --> O[Тот же Florence: вырезки CAPTION по одной]
    O --> R[Публикация готовых файлов]
    R -->|Полный комплект файлов| V
    R -->|Одна запись после сохранения файлов| DB[(PostgreSQL)]
    V -->|Автоматический показ через API| U
    U -->|Необязательная дополнительная копия| L[Папка на компьютере]
```

Пять контейнеров: frontend, backend, db, rabbitmq, worker. FastAPI сохраняет входные
файлы и синхронно публикует `image_id` с RabbitMQ publisher confirms; БД при загрузке
не используется. `202` подтверждает только принятие брокером. Если подтверждение
потеряно, входы остаются: сообщение уже могло быть доставлено.

Одна задача `process_image(image_id)` запускает RF-DETR Small и описание сцены
Florence-2-base-ft с `<DETAILED_CAPTION>` параллельно. После обеих веток тот же
загруженный Florence описывает все вырезки по одной с `<CAPTION>`.
Это уточнение от 20.10.2026 заменяет ViT-B/16 в приложении. Concurrency 1,
prefetch 1, batch 1: одновременно обрабатывается одно изображение.
Два потока координатора только обмениваются IPC; CUDA остаётся в двух постоянных
модельных процессах. Они загружаются и прогреваются до consumer; CUDA не
инициализируется в Celery prefork. Общий `storage/locks/inference.lock` удерживается
весь срок жизни моделей. Перед сравнением остановить worker. Хеши и параметры
сцены — `backend/checkpoints.json`; `backend/settings.py` задаёт prompt вырезок,
96 токенов и отступ 10%; сцена ограничена 256 новыми токенами.
Перед изменением весов/параметров завершить очередь и пересоздать worker.
При обычной ошибке модели другая ветка завершается до следующего изображения;
успешный комплект не создаётся. Прерывание координатора, ошибка IPC, таймаут
резидентного процесса или OOM отменяют активные запросы и требуют рестарта worker,
чтобы незавершённый ответ не попал в следующее изображение.
Реальное ускорение и запас RAM/VRAM при параллельной нагрузке пока не проверены.

## Файлы и данные

Входы: `image_data/<image_id>/original`, `normalized.png`. JPEG/PNG до 10 MiB и
25 Мп; проверить декодирование, кадры, EXIF orientation, нормализовать в RGB PNG.

После успеха всех трёх этапов комплект **всегда** сохраняется в
`image_data/results/<image_id>/`: `original`, `normalized.png`, `detection.png`,
`results.json` и папка `crops/` с PNG `<object_id>.png`. Имена вырезок перечислены
в поле `crops` файла `results.json`. При отсутствии объектов папка пустая. Временный каталог становится видимым через одно переименование;
файлы и каталог синхронизируются на диск. Входной каталог удаляется только после
commit БД. Основные файлы при скачивании не удаляются.

`detection.png` содержит исходные COCO bbox/labels. Florence получает целиком crop
с отступом 10% по ширине/высоте с каждой стороны в пределах изображения;
та же RGB-вырезка сохраняется в `crops/`. Нет преобразований ViT и дополнительной
центральной обрезки. Для сцены используется `normalized.png` без нарисованных рамок.
Детекция — `object_id`, `label`, `bbox` (xyxy в пикселях нормализованного PNG).
Раздел `classification.objects` сохраняется для совместимости JSONB; новые элементы
содержат `object_id` и исходный `object_caption`. Это описание, не ImageNet-класс
и не подтверждённый подтип. `annotation.raw_caption` сохраняется неизменным.
Нет объектов — пустой список описаний, описание сцены всё равно выполняется.
Старые комплекты с `label` и без `crops/` читаются без нового инференса и перезаписи.
Новые описания не проходят через словарь ImageNet→COCO.

Новая активная таблица `processed_images`: `id` (UUID PK), `original_path`,
`normalized_path`, `result_path`, `width`, `height`, `models`, `detection`,
`classification`, `annotation` (последние четыре поля — JSONB).
Одна строка — полностью обработанное изображение. Бинарные изображения находятся
в volume, в БД — пути и результаты. Нет записей заданий, статусов, ошибок, попыток,
промежуточных этапов, top-k, scores, хешей, повторных размеров и замеров.

Миграция `c81f0e392ab4` добавляет таблицу. По следующему запросу пользователя
от 20.10.2026 миграция `d20f4a6b819c` удаляет прежние `images`, `jobs`, `model_results`.
Старая история миграций сохранена; активная ORM содержит только `ProcessedImage`.
Перед необратимым удалением старых таблиц нужен дамп БД. Чистая установка
получает только `processed_images` и служебную `alembic_version`.
Старую очередь с `job_id` завершить прежним worker перед обновлением кода.

## Доставка и ошибки

RabbitMQ — durable exchange/queue `inference`, persistent JSON-сообщения,
late ACK и reject-on-worker-lost. Celery result backend, Redis, Beat, Flower не нужны.
Worker сначала проверяет доступность таблицы `processed_images`.

После инференса: сохранить файлы → commit PostgreSQL → ACK. Повторная доставка
готового UUID пропускает модели. Если файлы сохранены, но commit не прошёл,
worker после восстановления БД берёт `results.json` и повторяет только запись БД.
Потеря модельного процесса/координатора требует рестарта worker и redelivery.
До публикации файлов незавершённое изображение может быть обработано повторно целиком.

Ошибки моделей/файлов — в логах worker; готовая запись БД не создаётся. Входы остаются,
частичные ответы не записываются. Отдельного восстановления этапов, счётчиков попыток,
callback и сообщений об ошибках инференса пользователю нет. Гарантии exactly-once нет.
HTTP-валидация и ошибки доставки/скачивания сохраняются на границах системы.

## Интерфейс и дополнительная копия

По уточнению пользователя от 20.10.2026 frontend после загрузки автоматически
показывает PNG, исходное описание и таблицу. По следующему уточнению 20.10.2026
сохранена прежняя компоновка в две колонки: загрузка
и результаты под ней слева, картинка и отдельный большой блок «Результат аннотирования»
под ней справа. Исходное описание показано крупным текстом в этом блоке, а не в таблице.
Шапка с названием проекта и подсказка о выборе объектов убраны; панели начинаются сверху.
Ссылка API расположена рядом с «Отправить». Файл и папка выбираются в одну строку.
«Отправить» находится вне панели загрузки. При ширине от 1000 px используется высота
окна, длинная таблица прокручивается внутри панели; на узком экране — один столбец.
Браузер запрашивает `GET /images/{image_id}`, после `404` повторяет через 2 секунды;
после успеха/ошибки или новой загрузки опрос прекращается. Предел ожидания 40 минут,
таймаут одного запроса 15 секунд; при ошибке/истечении срока — «Повторить ожидание».
Таблица показывает COCO-класс и «Описание объекта» из `object_caption` по `object_id`.
Для старых комплектов без этого поля колонка пустая. GET сохраняет прежнее
вычисление `refinement` только для старых label; новые описания словарь не используют.
Файлы и БД не переписываются; `/jobs/...` и endpoint статуса не возвращаются.
Изображение справа располагается сверху под заголовком; рамки изображения
и результатов заканчиваются по содержимому, сохраняя внутреннюю прокрутку длинной
таблицы и ограничение высотой окна на ноутбуке.
Номера находятся только в таблице. Все рамки и названия COCO-классов постоянно видны
на картинке без номеров. Подписи внутри рамок, без фона, с подстройкой размера текста.
Нажатие объекта на картинке или номера/строки выделяет рамку и строку синим; остальные
рамки остаются ярко-красными (`#ff0000`, 2 px). При пересечении выбирается наименьшая содержащая точку рамка;
таблица прокручивается к ней. По умолчанию ничего не выбрано; повторное нажатие,
пустое место картинки или Escape снимает выделение.
Frontend рисует рамки и читаемые подписи поверх `normalized.png` по готовым bbox,
включая старые результаты без повторного инференса. Новые `detection.png` также
содержат только COCO-класс без номера; исходные ответы, bbox и БД не меняются.
Технический путь в volume в UI не выводится. Копия автоматически сохраняется в выбранную папку.
Дополнительная папка выбирается **на компьютере
пользователя**, в поддерживаемом браузере через File System Access API на localhost
или HTTPS. По следующему уточнению 20.10.2026 браузер автоматически записывает четыре основных файла и папку `crops`
в подпапку UUID после получения результата. Папку можно выбрать и после обработки —
запись начнётся сразу. При ошибке записи/потере разрешения результат остаётся видимым;
можно повторно выбрать папку или скачать ZIP. Без выбора папки или поддержки API
доступна кнопка «Скачать ZIP». Кнопок «Сохранить копию» и «Показать результат» нет.
Сохранение в volume обязательно в обоих случаях; состояние папки компьютера не передаётся серверу.

| API | Назначение |
|---|---|
| `POST /images` | Загрузка и непосредственная публикация в очередь; `202`: `image_id`, `output_folder`. |
| `GET /images/{image_id}` | Готовый результат с описаниями объектов; до готовности `404`. |
| `GET /images/{image_id}/files/{filename}` | Скачивание основного файла или `crops/<object_id>.png`. |
| `GET /images/{image_id}/archive` | Ручное скачивание полного ZIP. |
| `GET /health` | Проверка RabbitMQ для приёма загрузки. |

Доступ только по UUID к разрешённым именам внутри image volume. Авторизация, поиск,
редактирование, обучение, fine-tuning и LoRA не входят в текущий этап.

## Реализация и проверка

Слои API/service/repository сохранены: API — HTTP, service — загрузка/скачивание,
repository — готовые результаты БД, processing — последовательность и сохранение.
Новых сервисов и универсальных диспетчеров не добавлять.
CPU/mock-тесты и интеграцию PostgreSQL/RabbitMQ/отдельного Celery worker отличать
от настоящего GPU smoke. Новые реальные запуски моделей и сравнений этой задачей
не разрешены. Команды запуска, обновления и проверки — в [README.md](README.md).
